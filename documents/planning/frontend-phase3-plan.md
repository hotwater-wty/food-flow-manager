## 1. 背景:二期收口后的问题记录与审查结论

来源:用户二期收口后自总结的问题记录,叠加 2026-08-28 AI 对前端代码与后端契约的复核。立项时逐条审查结论如下。

### 1.1 用户问题记录的审查结论

| # | 问题记录 | 审查结论 |
| --- | --- | --- |
| 1 | 店长不应当能被禁用(前端标灰,后端审查兜底) | **成立且比预想紧急**。后端 `EmployeeServiceImpl.disableEmployee` 对角色无任何校验;而员工启用/禁用接口本身是店长专属权限——店长一旦被禁用将无人能执行启用,管理端整体死锁。前端标灰 + 后端 service 守卫,代码量小,适合顺手优化(P3-R1) |
| 2 | 大部分功能在数据有更新时需要手动刷新 | **属实**。全前端无任何轮询/自动刷新,12 个业务页均只在 `onMounted` 拉取一次,管理端工作台依赖手动点刷新。纯前端可解,不动后端(P3-R3) |
| 3 | 切换界面没有过渡效果(可参考 Ruo-Yi 淡入淡出) | **成立,低风险**。全工程无一处 `<transition>`/`<keep-alive>`,插入点仅三处(`App.vue` 与两个布局的路由出口);参考 Ruo-Yi 的 fade-transform 模式,顾客端 Vant 页面用更轻的动效(P3-R2) |
| 4 | 用户端和商户端还没拆分成独立前端工程 | **方向成立,时机后置**。后端已按 `/api/user` 与 `/api/admin` 干净分组,拆分天然对齐;但耦合点集中在 `services/http.ts`(URL 前缀嗅探选 token、路由路径嗅探跳 401)、单文件 `types/api.ts`、`utils/status.ts`、单 router、`tokens.css`,是全清单工作量最大的一项。本阶段只做共享层整理与成本评估,实际拆分另立阶段(P3-R4 + P3-R6) |
| 5 | 商户端加仪表盘,数据直观显示 | **可行,需后端最小配合**。后端目前不存在任何统计/聚合端点;订单表(金额分、状态、create_time 索引)与 order_item(菜品快照字段)足以支撑统计,新增一个只读端点即可。已确认:本阶段新增最小统计端点,前端接真实数据,不用占位假接口(P3-R5) |

### 1.2 自检补充发现(用户未列出,AI 复核发现)

1. **复制粘贴严重,无共享组件目录**:`formatPrice`(分→元)在 5 个视图重复实现(`AdminOrderWorkbenchView`、`CustomerOrdersView`、`CustomerMenuView`、`CustomerReservationCreateView`、`admin/DishesManageView`);订单/预约的状态标签颜色映射各视图近重复两份;`src/components/` 为空目录。
2. **`usePagedList` 未充分使用**:订单/会话工作台手工重复实现了该 composable 已封装的"页码+总数+加载锁+错误信息"状态机。
3. **顾客端订单/预约列表不分页**,全量拉取,数据增长后会劣化(候选池)。
4. **错误处理粗糙**:axios 响应拦截器只处理 401,网络错误无全局提示;401 跳转靠 URL 前缀嗅探,较脆弱(候选池)。
5. **购物车是页面级 ref**,切走再回来丢失(候选池,与 keep-alive 决策相关)。
6. 二期复盘第五节已登记的后置候选继续保留:组件库按需引入/分包、最小 E2E 脚本;R3/R4 遗留小缺陷:分类下拉只取第一页(pageSize 10)、SubmitBar 与 Tabbar 的 6px 缝隙、菜品表单未覆盖"售罄"状态。

## 2. 已确认决策

| 决策项 | 结论 |
| --- | --- |
| 仪表盘数据来源 | 新增 1 个最小只读统计端点(今日订单数/营收、订单状态分布、热销菜品 TOP N),不动表结构;前端直接接真实数据 |
| 双端拆分 | 本阶段只做共享层整理(P3-R4)与拆分成本评估(P3-R6);实际拆分等仪表盘等功能稳定后另立阶段,呼应后端未来微服务节奏 |
| 自动刷新方案 | 组合:管理端工作台轮询(可配置间隔、页面不可见暂停、可手动开关)+ 全部页面操作后即时刷新 + 窗口重新聚焦时拉取最新数据 |
| 过渡效果方案 | 参考 Ruo-Yi fade-transform:管理端路由出口加 fade-transform,顾客端加轻量 fade;不引入 keep-alive(页面缓存语义另议,避免购物车等状态被意外冻结) |
| 图表库 | R5 默认零依赖(Element Plus 组件 + CSS 呈现统计),如确需引入图表库(如 ECharts)在 R5 开工前单独报备确认 |

## 3. 切片清单(每片一个可验收检查点,完成后 git 提交并停点等用户确认)

### P3-R1 店长禁用限制:前端标灰 + 后端兜底守卫(已完成,2026-08-28)

- 前端:`admin/EmployeesManageView.vue` 中店长(role=2)行的"禁用"按钮标灰/隐藏,并给出不可禁用的原因提示(角色判断复用 `stores/admin-auth.ts` 的角色语义)。
- 后端:`EmployeeServiceImpl.disableEmployee` 增加角色守卫——拒绝禁用 MANAGER 角色;顺带评估并处理"自我禁用"(disable 自己的 employeeId)是否一并拒绝。
- 知识重点:前后端双重校验的分工(前端管体验、后端管安全)、computed 派生禁用状态、业务异常的契约表现。
- 验收:`pnpm type-check`(vue-tsc -b)与 build 通过;浏览器走查店长/店员双账号员工页;用浏览器或 curl 直调 `POST /api/admin/employees/{店长id}/disable` 返回业务错误而非成功;`git diff --check` 干净。

### P3-R2 路由切换过渡效果

- 三个插入点:`App.vue` 顶层路由出口(布局层切换,可选)、`AdminLayout.vue` 内容区路由出口(fade-transform)、`CustomerLayout.vue` 内容区路由出口(轻量 fade);过渡 CSS 进 `styles/`,类名与二期令牌体系一致。
- 前置核对:逐一确认各路由视图组件为单根节点(Vue transition 的前提),多根组件先包一层或调整结构。
- 知识重点:Vue `<transition>` 的工作机制(进入/离开类名、mode="out-in")、为何 router-view 需要配合 slot 写法。
- 验收:type-check 与 build 通过;双端双视口(1440x900 / 390x844)全页切换走查,无闪烁、无布局跳动、守卫跳转(登录/404)不受影响。

### P3-R3 数据刷新机制:工作台轮询 + 变更后刷新 + 聚焦刷新

- 管理端订单/会话工作台:加可配置间隔的轮询(默认 15~30s,常量集中定义),`document.hidden` 时暂停、恢复可见时立即拉取,提供手动开关;轮询与手动刷新共用加载锁,避免请求堆积。
- 全部页面审计:确认每次写操作(下单、状态推进、启停、删除等)后对应列表/详情即时刷新,补齐遗漏点。
- 窗口聚焦刷新:封装为组合式函数(如 `use-refreshOnFocus` 或并入现有 composable),顾客端关键页(订单/预约)接入。
- 知识重点:`setInterval` 与组件生命周期清理、`visibilitychange`/`focus` 事件、并发请求去重。
- 验收:type-check 与 build 通过;浏览器双端走查:工作台停放在页面观察自动更新、切走标签页暂停、操作后列表即时反映、聚焦回页面数据刷新。

### P3-R4 共享层整理(拆分准备 + 代码质量)

- `utils/format.ts` 补齐 `formatPrice`(分→元),替换 5 处视图内重复实现;`formatTime` 就地实现改用已有 `formatDateTime`。
- 订单/预约状态标签的 tag 类型映射收敛进 `utils/status.ts`,两两去重。
- 订单/会话工作台改用 `usePagedList`,删除手工分页状态机。
- 顺手修复 R3 遗留:分类下拉只取第一页的问题(pageSize 或全量拉取策略明确化)。
- 视抽取结果决定是否建立 `src/components/` 首批共享组件(如状态标签),不强求。
- 知识重点:DRY 与模块边界、composable 复用、"共享层干净 = 未来拆分成本低"的工程视角。
- 验收:type-check 与 build 通过;走查订单工作台、会话工作台、菜品页、顾客端订单/预约页行为与改版前一致(纯重构,行为不变);diff 中无业务逻辑变化。
