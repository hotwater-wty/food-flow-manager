## 1. 当前阶段定位

项目已经具备可运行的单门店堂食主流程：顾客登录、预约、首页选座开台、点餐和查单；员工登录、订单处理、会话清台、资料维护和经营概览。前端已经拆为两个 Vite 应用，管理端写操作反馈与布局级 SSE 已落地。

下一阶段不应继续零散堆页面，也不建议立即拆微服务。当前最明显的短板是后端自动化测试、生产级认证与部署、预约模型的业务真实性，以及新增业务缺少稳定契约和审计能力。推荐顺序是“先建立可靠回归网，再补后端契约与业务规则，然后引入前后端新业务，最后做生产部署”。

## 3. 新发现的关键欠账

### 3.1 后端测试基础薄弱

当前后端只有 3 个测试类、6 个 `@Test`，主要覆盖 Spring 上下文、`Result` 和 SSE ticket；预约、开台、下单、状态推进、清台、权限、缓存和并发没有自动化回归。前端继续扩展前，建议先建立隔离的 `test` profile，并用 Testcontainers 或等价方式提供可重复的 MySQL/Redis 环境。

### 3.2 预约模型不符合真实时间段语义

当前创建未来预约会立即把桌位置为 `RESERVED`，直到到店或取消前其他顾客都不能使用，无法表达“同一桌今天中午使用、晚上被预约”。源码也保留了相关 TODO。若项目继续强调“预约”能力，应优先设计预约时段、冲突区间、迟到过期和自动释放，而不是先增加更多预约页面。

### 3.3 首页直接开台只适合当前开发阶段

直接选择桌位能完成开发和演示闭环，但公开部署后，未到店用户也能远程占用空闲桌位。二维码继续暂停，不要求立即恢复；生产化前必须增加一种店内证明或员工确认机制，可选方案包括桌位短码、员工批准、一次性开台码或后续二维码。

### 3.4 数据库演进和生产配置缺少治理

当前依赖初始化 SQL，没有版本化迁移工具；正式环境密码和 JWT 密钥也需要外部配置。业务表继续演进前应评估 Flyway/Liquibase、环境变量/Secret、备份恢复和回滚流程。

## 4. 推荐路线

### 阶段 P0：可靠性基线（最高优先）

目标：让现有主流程可重复验证，再开始新增业务。

1. 建立后端 `test` profile 和可隔离的 MySQL/Redis 测试环境。
2. 为预约、直接开台、创建订单、订单推进、清台补 Service/集成测试，覆盖成功、权限、冲突、重复和事务回滚。
3. 建立 GitHub Actions：后端测试、前端 type-check/lint/format/build/unit/E2E；CI 稳定后再决定是否加 Husky。
4. 建立业务错误码注册表，先覆盖桌位占用、会话冲突、非法状态推进、权限和提交令牌。
5. 评估数据库版本迁移工具，避免后续只修改初始化 SQL。

验收出口：全新环境可一条命令运行测试；核心状态机有自动化保护；PR 或 push 能自动给出通过/失败结果。

### 阶段 P1：现有能力补全（后端先行，前端跟进）

1. 顾客订单和预约分页：后端返回 `PageResult`，前端增加分页/加载更多和筛选状态。
2. 员工编辑、离职流程：明确离职是否可恢复、旧 JWT 如何失效，前端补编辑入口和状态展示。
3. 顾客账号管理：店长可查询、禁用/启用顾客，所有动作写入审计日志。
4. JWT 生命周期：短期 access token、refresh token 或服务端会话二选一；支持主动登出和强制失效。
5. 桌位全状态只读接口：仅在确有展示需求时加入；开台仍由后端原子校验，不能信任前端状态。

验收出口：接口契约、权限和分页稳定；前端不再加载无限增长的用户列表；员工/顾客状态具有完整业务闭环。

### 阶段 P2：预约业务重构（推荐的首个新业务）

1. 定义营业时段、预约时长、最晚到店时间和桌位冲突区间。
2. 创建预约不再永久锁桌，按时间窗口判断冲突。
3. 定时任务处理预约过期并释放资源；SSE 通知管理端预约变化。
4. 顾客端展示可预约时段，管理端提供当日预约时间轴或筛选视图。
5. 为并发预约、取消与到店竞态补自动化测试和稳定错误码。

选择原因：它修复当前模型最明显的业务失真，同时能自然练习数据库查询、事务、定时任务、前后端契约和实时通知。

### 阶段 P3：运营能力

1. 操作审计日志：记录操作者、动作、对象、前后状态、结果、时间和请求追踪 ID。
2. 近 7/30 日趋势端点与仪表盘图表；先确定统计口径，再选择 ECharts。
3. 通知中心：SSE 继续做实时提示，数据库保存需要追溯的通知，避免“断线即丢失”。
4. SSE 生产化：心跳、代理配置、连接指标、多实例 Pub/Sub；单实例阶段不要提前引入 MQ。
5. 可观测性：结构化日志、请求 ID、Actuator 指标和关键业务失败计数。

### 阶段 P4：生产部署

1. admin/customer 双域名或同域不同子路径的 nginx 配置。
2. 两个前端静态镜像与 Compose/部署仓库边界。
3. HTTPS、CORS、SSE 禁用代理缓冲、长连接超时和安全响应头。
4. 外部化数据库密码、Redis 密码和 JWT 密钥；建立数据库备份恢复演练。
5. CI/CD 分环境部署、健康检查和回滚。

### 阶段 P5：可选新业务（需要先做产品决策）

| 方向 | 前置决策 | 建议 |
| --- | --- | --- |
| 加菜/改单/退单 | 订单快照、金额重算、厨房已制作后的处理规则 | 比支付更贴近堂食流程，可在预约重构后优先评审。 |
| 呼叫服务/催单 | 频率限制、处理状态、是否需要历史记录 | 可复用 SSE，但必须有持久化记录，不能只发瞬时事件。 |
| 结账/支付 | 支付渠道、回调幂等、退款、对账、安全合规 | 工作量和风险高，除非项目目标明确要求，不作为近期任务。 |
| 库存/售罄 | 库存粒度、扣减时点、超卖处理 | 当前只有人工售罄状态；需要真实库存目标时再设计。 |
| 多门店/排班 | 数据隔离、角色模型、门店上下文 | 会改变几乎所有表和权限，不建议在当前单门店阶段启动。 |

## 5. 不建议近期实施

- 不为展示技术栈而立即拆微服务。先用模块边界测试、审计、CI 和稳定契约把模块化单体做好。
- 不同时引入 MQ、分布式锁和复杂缓存治理。当前单实例 SSE 与数据库事务足以支持现阶段，按真实瓶颈演进。
- 不直接把二维码恢复为必做项。先决定生产开台的店内证明方式，再选择二维码、短码或员工确认。
- 不把 Husky 当作 CI 替代品；本地钩子可跳过，远端门禁才是团队协作事实。

## 6. 执行规则与推荐下一片

每次只从本计划启动一个可验收切片。启动前输出任务简报，明确业务目标、契约、允许修改文件、失败场景、测试数据和回滚方式；完成后更新本文件状态、相关事实文档和验收记录。

推荐下一片是 **P0-1：后端测试基线设计与首条“直接开台”集成测试**。它不增加业务范围，能先验证测试容器、数据库初始化、登录上下文、成功开台和桌位占用冲突，为之后所有后端迭代建立模板。

需要用户先决定的不是技术细节，而是下一阶段主线：

1. 先补可靠性基线（推荐）。
2. 直接重构预约时间段业务。
3. 先做生产部署。
4. 选择一个 P5 新业务先完成产品规则评审。
