# 领域模型与核心表

> 文档状态：当前事实
> 校准日期：2026-08-22
> 事实来源：`backend` 实体类、枚举、Mapper、Service 和 `assets/schema.sql`

## 1. 聚合对象

| 对象 | 关键字段 | 当前职责 |
| --- | --- | --- |
| `User` | phone、nickname、status | 用户认证和用户端业务归属 |
| `Employee` | phone、name、role、status | 员工认证、店长授权和管理操作 |
| `DiningTable` | tableNo、capacity、status、currentSessionId | 当前桌位资源和活跃会话指针 |
| `Reservation` | reservationNo、userId、tableId、peopleCount、reserveTime、status | 未来到店资源占用 |
| `DiningSession` | sessionNo、userId、tableId、reservationId、status、activeFlag | 一次实际占座/用餐上下文 |
| `DishCategory` | name、sort、status | 菜品分类和用户可见分类 |
| `Dish` | categoryId、name、price、image、description、status | 菜品资料和售卖状态 |
| `DiningOrder` | orderNo、userId、tableId、sessionId、totalAmount、status | 一次堂食订单 |
| `OrderItem` | orderId、dishId、dishName、dishPrice、quantity、amount、remark | 下单时菜品快照和明细 |

## 2. 状态枚举

状态码以 `backend/src/main/java/com/foodflow/common/enums` 和 schema 注释为准：

- 用户：正常 1、禁用 2。
- 员工：正常 1、禁用 2、离职 3；角色为店员 1、店长 2。
- 桌位：空闲 0、已预约 1、等待中 2、用餐中 3、禁用 4。
- 预约：待到店 0、已到店 1、已取消 2、已超时 3。
- 会话：等待中 0、用餐中 1、已完成 2、已取消 3；活跃标识只有 1，非活跃用 NULL 表示。
- 分类：启用 1、禁用 2。
- 菜品：停售 0、启售 1、售罄 2。
- 订单：已下单 1、制作中 2、已上齐 3、已完成 4、已取消 5。

## 3. 关系与约束

- 一个用户可以有多条预约和历史订单，但同一时间最多一个活跃会话。
- 一个桌位通过 `current_session_id` 指向当前活跃会话。
- 一个会话可来自预约或直接扫码；当前创建订单流程围绕会话归属用户校验。
- 一个会话可以关联多个订单，当前首期 UI 只规划一个主订单闭环。
- `dining_session` 的 `(user_id, active_flag)` 和 `(table_id, active_flag)` 唯一索引利用 MySQL 对 NULL 的处理限制活跃会话重复。
- 数据库未建立物理外键，关联存在性、归属和状态由 Service 校验。
- 订单明细保存菜品快照字段，不依赖菜品当前名称、价格或图片。

## 4. 表结构范围

`assets/schema.sql` 当前创建：`user`、`employee`、`dining_table`、`reservation`、`dining_session`、`dish_category`、`dish`、`dining_order`、`order_item`。

已落地的索引包括手机号、业务编号、状态、时间、关联 ID 和活跃会话唯一索引。脚本还会初始化默认店长和基础菜品分类。

## 5. 当前未建模能力

没有独立表的能力包括支付、短信验证码、购物车持久化、追加订单、退单/改单、排班、操作日志、订单状态历史、动态权限和多门店。它们是候选需求，不是当前领域模型的一部分。

## 6. 变更要求

字段、索引、枚举或主流程关系变化时，必须同步实体、schema、Service 校验、接口 VO 和本文，并在设计更新日志记录日期、原因和验证结果。
