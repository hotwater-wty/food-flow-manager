# 项目实践学习 Skill 封存记录

> 文档状态：问题记录
> 记录日期：2026-08-23
> 当前执行入口：[`../../planning/frontend-development-plan.md`](../../planning/frontend-development-plan.md)

## 现象

`project-practice-learning` 内置的“小白版 + 专业版”解释模板用于单个陌生概念时效果较好，但对 `main.ts`、Router、Pinia、Axios、Vite 代理和 TypeScript 类型边界等多个知识点分别讲解后，内容不容易串联成完整工程认识。

## 原因判断

模板的组织单位是“单个概念”，当前项目学习真正需要的组织单位则是“纵向业务切片及其运行链路”。原 Skill 缺少：

- 当前任务在总体业务流和工程结构中的位置。
- 入口、路由、状态、请求、类型和后端契约之间的数据流。
- 从局部代码回到模块职责和协作边界的阶段复盘。
- 根据用户实际掌握情况选择解释深度的机制。

继续扩展 Skill 会在当前阶段引入较高的配置、试验和维护成本，因此不立即重写。

## 当前处理

- Skill 已从 `~/.codex/skills/` 移至 `~/.codex/archived-skills/`，不再参与自动发现。
- 封存副本保留原始内容，并将 `allow_implicit_invocation` 设为 `false`。
- 项目继续保留“展开下一步先给任务简报，用户选择分工后再编码”的规则。
- 取消对每个重要知识点强制使用双层模板，改为先交代工程位置，再按实际卡点解释。

## 后续重做方向

未来重做时采用四层结构：

```text
工程地图
  -> 当前纵向切片及运行链路
  -> 本轮概念之间的关系
  -> 单个陌生概念的按需解释
```

双层解释模板只作为按需工具，不再作为每个任务的固定产出。恢复自动触发前，需要用跨多个知识点的真实任务重新验证。
