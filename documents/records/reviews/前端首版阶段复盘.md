# 前端首版阶段复盘

> 文档状态：阶段记录
> 记录阶段：前端首版顾客与商户闭环
> 当前入口：[`documents/CURRENT.md`](../../CURRENT.md)
> 计划入口：[`documents/planning/frontend-development-plan.md`](../../planning/frontend-development-plan.md)
> 说明：本文记录当前前端首版的实际完成范围、验证证据和遗留边界，不替代接口契约。

## 1. 本阶段目标

前端首版采用真实后端纵向闭环，而不是先批量制作静态页面：

```text
顾客登录
  -> 预约或模拟扫码开台
  -> 菜单与前端购物车
  -> 创建订单
  -> 查看订单
  -> 员工登录
  -> 管理订单状态
  -> 管理会话并清台
```

阶段 6 已完成第二批资料工作台、顾客注册补充切片、真实数据验收和文档收尾。

## 2. 已完成能力

### 顾客端

- 顾客登录、Token 持久化、刷新恢复、401 回登录。
- 空闲桌位查询、预约创建、预约列表/详情/取消。
- 非预约模拟扫码开台、预约到店开台、当前会话恢复。
- 菜品分类、可售菜品筛选、内存购物车。
- `create-order` 一次性提交令牌、订单创建、订单列表和详情。

### 商户端

- 员工登录和独立员工认证 Store。
- 管理订单分页、详情和合法状态推进。
- 管理会话分页、取消等待和清台。

## 3. 工程边界与关键决策

1. 顾客和员工使用不同 Token 存储与请求选择逻辑，避免角色凭证混用。
2. 前端购物车是订单提交前的临时输入，不是后端持久化购物车；后端订单金额和状态是最终事实。
3. 顾客端列表使用普通数组，管理端列表遵循真实 `PageResult` 分页结构。
4. 页面状态按加载、空、失败、成功和提交中拆分；成功写操作后重新读取服务端数据。
5. 第二批资料使用统一管理工作台，避免为每类资源复制一套相同的分页和表单基础结构。

## 4. 验收证据

### 命令级

```text
cd frontend && pnpm type-check
cd frontend && pnpm build
cd frontend && pnpm verify:api
git diff --check
cd backend && ./mvnw test
```

以上命令在本轮阶段 6 收尾中通过；`verify:api` 使用默认顾客和店长测试账号，只验证真实接口响应结构，不创建或删除业务数据。后端 Maven 测试运行 1 个测试，失败数为 0。

### 接口级

- 后端健康检查返回 `{"status":"UP"}`。
- 顾客测试账号 `13900001234` 登录成功。
- 默认店长账号 `18800000000` 登录成功。
- 管理端订单接口返回合法分页结构：`total/pageNo/pageSize/records`。
- 管理端会话接口返回合法分页结构。
- 员工 Token 不能作为顾客接口凭证使用。
- 初始验收时数据库没有空闲桌位、可售菜品、订单和会话，首轮只能验证空状态；本轮已补充可控数据完成主要成功链路。
- 本轮已补充一套本地验收数据，完成桌位、菜品、非预约开台、创建订单、订单状态推进、清台、预约创建和预约到店开台成功链路；预约响应中的 `tableNo` 为空问题已记录并在前端增加 `tableId` 显示兜底。

验收结束后使用 `docker compose stop`，保留容器、镜像和数据卷。

## 5. 遗留问题

- 准备可控测试数据，复验预约成功、开台成功、菜单有数据、创建订单和订单详情成功分支。
- 管理端订单和会话需要浏览器级有数据验收，而不只依赖接口空列表。
- 当前页面样式仍是首版工程样式，尚未进入个性化视觉和组件库统一阶段。
- 前端仍缺少系统化单元测试和端到端自动化测试。

## 6. 阶段结论

原有前端计划中的顾客闭环、商户闭环、第二批资料工作台、真实数据复验、API 冒烟检查、浏览器路由保护和文档复盘均已完成。支付、真实二维码、持久化购物车、退单/改单、排班、库存和复杂运营报表仍属于后端当前明确的未实现候选能力，不纳入本阶段完成度。

## 7. 学习复盘

本阶段最重要的工程认识不是记住某个 Vue API，而是理解前端在系统中的边界：页面组织用户操作，服务层表达 HTTP 契约，Store 管理认证上下文，后端负责业务事实和状态机。后续学习应继续围绕“一个用户动作如何经过组件、服务层、认证、后端状态和验收证据完成闭环”展开。
