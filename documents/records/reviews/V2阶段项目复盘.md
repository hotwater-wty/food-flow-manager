# V2 阶段项目复盘

> 文档状态：历史记录
> 记录阶段：V2 后端工程增强
> 当前事实入口：[后端技术选型与当前依赖](../../architecture/backend/技术选型与依赖规划.md)
> 说明：本文保留 V2 阶段复盘；当前实现以源码和架构文档为准。

本文档用于复盘 `food-flow-manager` 从 V1 主流程闭环进入 V2 工程增强阶段后的开发过程。它不是接口文档，也不是全部变更清单，而是面向未来复述项目、准备面试、规划后续迭代时可直接使用的阶段性总结。

## 1. V2 阶段目标与最终结果

V1 阶段已经完成了餐饮预约与堂食管理的最小业务闭环：

```text
用户预约桌位
  -> 到店扫码开台
  -> 查看菜品
  -> 创建堂食订单
  -> 商户处理订单
  -> 店员清台释放桌位
```

V2 阶段没有推翻 V1 的业务模型，而是围绕后端工程能力做增强。核心目标是让项目从“主流程能跑通”升级为“主流程在常见工程场景下更可靠、更可维护、更容易部署和展示”。

本阶段主要完成了：

- 对预约、扫码开台、非预约开台、创建订单、清台等关键状态流转补强并发控制。
- 为活跃开台会话增加 `active_flag` 与唯一约束思路，避免一个用户同时存在多个活跃会话。
- 使用 MyBatis-Plus 分页插件统一管理端列表接口的分页返回结构。
- 引入 Redis，落地启售菜品列表、菜品详情、启用分类、账号状态和防重复提交令牌等缓存场景。
- 抽取 `CacheUtil` 与业务缓存 Client，减少 Service 中散落的 JSON 序列化、空值缓存和 Redis 操作细节。
- 使用 Redis 实现防重复提交令牌，保护创建预约、创建订单等关键写接口。
- 使用 Docker Compose 编排 MySQL、Redis 和后端服务，并将 Dockerfile 改造为多阶段构建，实现 clone 后一键构建启动。
- 更新 README，使项目具备更清晰的对外展示和部署说明。

## 2. 项目推进过程

V2 的推进顺序基本沿用了开发计划中设定的路线：

```text
V2 基线检查
  -> 并发控制与数据一致性
  -> 管理端分页查询
  -> Redis 缓存落地
  -> Docker Compose 部署增强
  -> README 与过程资产收束
```

第一步是确认 V1 主流程不被破坏。V2 的所有增强都围绕已有链路展开，避免为了引入技术点而重写业务模型。

第二步优先处理并发问题。预约、扫码开台、创建订单、清台这些接口都会改变桌位、预约、开台会话和订单状态。如果只依赖“先查状态再改状态”，在并发请求下容易出现重复预约、重复开台、重复下单或重复清台。因此 V2 优先使用数据库条件更新和唯一约束来兜住主流程可靠性。

第三步补齐分页查询。V1 阶段为了快速闭环，管理端很多列表接口直接返回全量数据。V2 通过 `PageQueryDTO`、`PageResult<T>` 和 MyBatis-Plus 分页插件统一接口风格，使管理端接口更接近真实后台系统。

第四步引入 Redis。项目没有一上来就堆复杂缓存治理，而是选择与当前业务强相关的读多写少场景，例如启售菜品、菜品详情、分类列表和账号状态。同时补充防重复提交令牌，形成一个可讲清楚的 Redis 写接口保护场景。

第五步完善部署。Docker 部署最初需要手动打 jar、复制并改名，流程偏开发者操作。后续改为 Docker 多阶段构建，使部署者只需要 clone 仓库并执行 `docker compose up -d --build`。

## 3. 核心业务闭环复盘

V2 没有新增一条完全独立的新业务链路，而是对 V1 主链路进行可靠性补强。

创建预约时，核心状态变化是桌位从空闲进入已预约，并创建预约记录。V2 中重点是避免多个用户并发预约同一桌位，因此使用条件更新让数据库参与状态判断：只有桌位仍处于目标状态时才允许更新。

预约扫码开台时，核心状态变化是预约变为已到店、桌位进入等待点餐状态、创建开台会话。V2 中重点是避免同一预约被重复核验，或同一用户出现多个活跃会话，因此需要同时依赖业务层状态校验、条件更新和活跃会话唯一性约束。

非预约扫码占座时，核心状态变化是桌位从空闲进入等待点餐，并创建开台会话。V2 中重点是避免多人同时扫码占用同一桌位，以及同一用户重复创建活跃会话。

创建订单时，核心状态变化是等待中的开台会话进入用餐中，桌位进入用餐中，并创建订单及订单明细。V2 中重点是避免重复下单和状态覆盖，并处理菜品明细与菜品主数据之间的稳定映射。

清台释放桌位时，核心状态变化是订单完成、开台会话完成、桌位恢复空闲、活跃标记释放。V2 中重点是避免重复清台造成状态覆盖，并确保清台逻辑在跨表操作时仍由事务保护。

## 4. 关键设计决策复盘

### 4.1 并发控制优先使用数据库条件更新和唯一约束

当时的问题：

V1 中很多状态流转是“查询实体 -> 判断状态 -> 修改状态”。单次请求内逻辑正确，但并发请求可能在同一旧状态下同时通过校验。

可选方案：

- 使用 synchronized 或 JVM 本地锁。
- 使用悲观锁。
- 使用 Redis 分布式锁或 Redisson。
- 使用数据库条件更新和唯一约束。

最终选择：

V2 优先使用数据库条件更新和唯一约束。原因是当前项目仍是单体后端，核心竞争资源最终都落在 MySQL 表上，数据库条件更新能直接把“状态仍为预期值”写入更新条件，并通过影响行数判断并发冲突。

适合 V2 的原因：

- 技术复杂度适中，能解释清楚。
- 不依赖额外分布式锁组件。
- 直接保护最终数据。
- 适合预约、开台、下单、清台这类状态机式业务。

V2 之后的升级方向：

如果后续出现多实例部署、跨服务资源竞争或需要控制外部副作用，可以再评估 Redis 锁、Redisson、消息队列或更完整的幂等表方案。

### 4.2 使用 active_flag 约束活跃开台会话

当时的问题：

业务上一个用户同一时间只应该有一个等待中或用餐中的开台会话。如果只在 Service 层查询“当前是否已有活跃会话”，并发或脏数据仍可能绕过检查。

最终选择：

为开台会话引入 `active_flag` 思路：等待中、用餐中为活跃状态，完成或取消后释放活跃标记。配合唯一约束，可以把“一个用户最多一个活跃会话”的规则下沉到数据库层。

经验价值：

这类设计不是为了替代业务校验，而是让业务规则形成双保险：

```text
Service 层提前判断，给出友好错误
数据库唯一约束兜底，防止并发和脏数据突破规则
```

### 4.3 分页查询统一使用 PageResult

当时的问题：

管理端列表接口逐渐增多，如果每个接口自己定义分页字段、返回结构和总数信息，后续维护成本会变高。

最终选择：

使用 MyBatis-Plus 分页插件，并统一通过 `PageResult<T>` 返回：

- 当前页数据。
- 总记录数。
- 当前页码。
- 每页大小。

适合 V2 的原因：

分页是后台系统的基础能力，复杂度适中，且能明显提升接口规范性。相比直接返回 `List<T>`，分页返回更适合后续接前端、Apifox 测试和接口文档展示。

### 4.4 Redis 先落地缓存和防重复提交，不急于做分布式锁

当时的问题：

Redis 可用场景很多：缓存、验证码、限流、防重复提交、分布式锁、消息队列辅助等。如果一次性全面引入，容易变成堆技术。

最终选择：

V2 优先落地两类清晰场景：

- 读多写少缓存：启售菜品、菜品详情、启用分类、账号状态。
- 写接口保护：防重复提交令牌。

暂不优先做 Redis 分布式锁。当前主流程并发主要通过数据库条件更新和唯一约束解决，Redis 锁不是必须项。

经验价值：

中间件不应为了出现而出现。Redis 在本项目中的价值是解决明确问题：减少高频读数据库、降低账号状态查询成本、保护关键写接口免受重复提交。

### 4.5 缓存访问细节从 Service 抽离

当时的问题：

Redis 缓存刚落地时，Service 中容易散落大量类似逻辑：

```text
查 Redis
判断空字符串
ObjectMapper 反序列化
缓存未命中查数据库
写缓存
异常处理
```

这些逻辑如果分散在各个 Service 中，会让业务流程被缓存细节污染。

最终选择：

抽取 `CacheUtil` 处理通用缓存读写和 JSON 序列化，使用业务缓存 Client 封装具体缓存 key 和业务含义。并通过 `CacheResult<T>` 区分命中、未命中、空值缓存。

适合 V2 的原因：

当前项目缓存场景已经超过一个模块，抽取工具类和业务 Client 能减少重复代码，但仍保持足够简单，没有过早引入复杂缓存框架。

### 4.6 Docker 部署改为多阶段构建

当时的问题：

早期部署流程要求服务器手动执行 Maven 打包、复制 jar、改名，再由 Docker Compose 启动。这对开发者可接受，但对部署者不够友好。

最终选择：

使用 Docker 多阶段构建：

- 构建阶段使用 JDK 镜像执行 Maven 打包。
- 运行阶段使用 JRE 镜像运行最终 jar。
- Docker Compose 统一编排 MySQL、Redis 和后端服务。

结果：

部署流程收敛为：

```bash
git clone ...
cd food-flow-manager
docker compose up -d --build
```

该流程已经在 Ubuntu 24 虚拟机中验证成功。

## 5. 典型问题与解决过程

### 5.1 对并发工具的定位不清晰

问题表现：

学习并发控制时会同时接触乐观锁、悲观锁、Redis 锁、Lua、Redisson 等概念，容易误以为项目没有使用这些高级工具就不够可靠。

解决过程：

结合当前项目分析后明确：项目的核心并发冲突发生在数据库状态字段上，优先用数据库条件更新和唯一约束更直接。Redis 锁不是可靠性的唯一表达，关键是约束是否落在最终数据上。

最终收获：

并发控制要先定位资源和冲突点，再选择工具。工具越复杂不代表越适合，当前项目的主链路可靠性主要由事务、条件更新、唯一约束和业务校验共同保证。

### 5.2 Redis JSON 泛型反序列化问题

问题表现：

使用 Redis 缓存启售菜品列表时，写入 JSON 后第二次读取缓存失败，报错指向 JSON 反序列化。

根因：

集合泛型在运行期容易丢失，仅传入 `List.class` 无法告诉反序列化器集合元素应恢复为 `DishVO`。

解决方式：

改用 `StringRedisTemplate + ObjectMapper`，读取复杂泛型结构时传入 `TypeReference<List<DishVO>>`，让 ObjectMapper 获得完整类型信息。

最终收获：

缓存对象如果是复杂泛型，不要只依赖 `Class<T>`。单对象可以用 `DishVO.class`，集合对象应使用 `TypeReference<List<DishVO>>`。

### 5.3 空值缓存与缓存不存在需要区分

问题表现：

如果缓存读取返回 `null`，无法区分是 Redis 中没有该 key，还是业务上缓存了“空对象”。

解决方式：

引入 `CacheResult<T>` 和缓存状态枚举，明确区分：

- `HIT`：命中有效数据。
- `MISS`：缓存不存在，需要回源数据库。
- `EMPTY`：命中空值缓存，不需要回源。

最终收获：

缓存层不应只返回裸数据。只要业务需要区分缓存状态，就应该返回带状态的结果对象。

### 5.4 OpenAPI 扫描范围导致新增接口不显示

问题表现：

新增防重复提交令牌接口后，Knife4j 页面没有出现对应接口。清浏览器缓存、重新构建都无效。

根因：

OpenAPI 配置只扫描 `com.foodflow.module`，而新增的通用 Controller 位于 `com.foodflow.common.controller`。

解决方式：

扩大扫描范围到 `com.foodflow`。

最终收获：

接口文档缺失不一定是浏览器缓存或注解问题，也可能是 OpenAPI 扫描包配置与代码包结构不一致。

### 5.5 Docker 部署流程从开发者流程变成部署者流程

问题表现：

早期 Docker 部署需要手动打 jar、复制到项目根目录并改名。虽然可用，但步骤偏多，容易出错。

解决方式：

改造 Dockerfile 为多阶段构建，并配合 `.dockerignore` 控制构建上下文。部署者只需 clone 仓库后执行 `docker compose up -d --build`。

最终收获：

部署文档不应只追求“能跑”，还要考虑使用者操作成本。好的部署流程应该尽量减少手工中间步骤。

## 6. 当前 V2 的边界与不足

V2 已经完成了主要工程增强，但仍有一些边界需要明确。

自动化测试仍不充分。当前主要依赖 Apifox 接口验证和手动流程测试，虽然主流程和部署流程已经跑通，但缺少系统化的集成测试、并发测试和缓存测试。

缓存治理仍是基础版。当前实现了缓存读取、写入、清理、空值缓存和防重复提交，但还没有系统处理缓存穿透、击穿、雪崩、预热和监控。

权限体系仍是自定义拦截器方案。对于当前角色模型足够使用，但如果后续权限规则继续复杂化，可能需要评估 Spring Security。

并发控制主要围绕单体和数据库状态流转。当前并发问题已经通过条件更新、唯一约束和事务得到较好的基础保障，但如果未来演进到多实例、跨服务或引入外部副作用，还需要重新评估幂等表、消息可靠性和分布式锁。

业务增强还未展开。预约超时、操作日志、消息通知、定时任务、催单、追加订单等仍属于后续阶段。

## 7. 面试表达整理

### 7.1 30 秒项目介绍

这是一个基于 Spring Boot 3 的餐饮预约与堂食管理后端项目。V1 完成了用户预约、到店开台、查看菜品、创建订单、商户处理订单、店员清台的完整业务闭环。V2 在此基础上补强了关键状态流转的并发控制、管理端分页查询、Redis 缓存、防重复提交令牌和 Docker Compose 部署，使项目从“功能能跑通”进一步提升到“具备工程可靠性和部署能力”。

### 7.2 2 分钟业务流程介绍

项目面向单门店堂食场景。用户登录后可以查看空闲桌位并创建预约，到店后通过预约扫码开台，或者直接扫码占座。开台后系统创建 `dining_session` 作为用餐上下文，用户可以查看启售菜品并创建订单。商户端员工查看订单并按状态处理，最终店员清台，系统完成订单、开台会话和桌位状态的收束。

这个流程中最关键的是状态流转。桌位会在空闲、已预约、等待点餐、用餐中之间切换；预约会从待到店变为已到店或已取消；开台会话会从等待中变为用餐中再到完成；订单会从已下单流转到制作中、已上齐、已完成。V2 中我重点补强了这些状态流转的并发安全，使用数据库条件更新和唯一约束避免重复预约、重复开台、重复下单和重复清台。

同时，项目引入 Redis 缓存启售菜品、菜品详情、分类列表和账号状态，并用 Redis 实现防重复提交令牌。部署上使用 Docker Compose 编排 MySQL、Redis 和后端服务，并通过多阶段 Dockerfile 实现 clone 后一键构建启动。

- 为什么 V2 优先使用数据库条件更新和唯一约束，而不是 Redis 分布式锁？
- `active_flag` 如何约束一个用户只能有一个活跃开台会话？

## 8. 对后续 V3 的启发

V2 之后，项目已经具备较完整的后端工程骨架。后续不建议继续零散堆功能，而应围绕“可观测、可测试、可异步、可配置”选择少数主线继续深化。

优先方向可以是自动化测试。补齐主流程集成测试、并发测试和缓存测试，能让现有代码更稳，也能补上当前 V2 最大短板。

第二个方向是操作日志。预约、开台、订单、桌位、菜品和员工管理都有状态变化，操作日志既有业务价值，也有排查和面试表达价值。

第三个方向是定时任务。预约超时自动取消、长时间等待提醒、长时间未处理订单提醒都适合用定时任务落地，并且与当前业务自然相关。

第四个方向是消息队列。可以选择订单创建后通知商户端或操作日志异步落库作为单一场景，不建议一开始全面引入 MQ。

第五个方向是权限体系升级。当前自定义 JWT 拦截器足够支撑 V1/V2，但如果后续出现更细粒度权限、接口权限矩阵或多角色扩展，可以评估迁移到 Spring Security。

## 9. 阶段总结

V2 阶段最大的价值不是新增了多少业务接口，而是把 V1 的主业务闭环向真实后端工程靠近了一步。

从业务角度看，主流程仍然保持清晰：预约、开台、点餐、处理订单、清台。

从工程角度看，项目补上了并发约束、分页查询、Redis 缓存、防重复提交和 Docker 部署。

从个人成长角度看，本阶段真正重要的是形成了一套判断方式：

```text
先定位业务问题
再判断问题属于状态一致性、性能、权限、部署还是可维护性
最后选择足够解决当前问题的技术方案
```

这也是后续继续迭代项目时应保持的节奏。
