# 过程记录维护手册

> 文档状态：当前维护规范
> 更新日期：2026-08-22

过程记录解释一个结论如何形成，不替代当前设计。当前行为写入 `architecture/` 或 `frontend/`，问题、取舍、经验和阶段证据写入 `records/`。

## 1. 五类记录

| 类型 | 位置 | 记录重点 | 停止标准 |
| --- | --- | --- | --- |
| 问题 | `records/issues/` | 现象、根因、修复和验证 | 能复现并验证修复 |
| 决策 | `records/decisions/` | 背景、选项、取舍和适用边界 | 能说明为何这样选 |
| 实践 | `records/practices/` | 从项目抽象出的工程方法 | 能在同类问题复用 |
| 专题 | `records/topics/` | 某项技术在当前项目的真实用法 | 示例与源码现状一致 |
| 复盘 | `records/reviews/` | 阶段目标、结果、证据和遗留项 | 阶段已结束且边界清楚 |

普通拼写修正、一次性命令输出和没有复用价值的小错误不沉淀。

## 2. 当前事实与过程证据的边界

- Controller 当前有哪些接口，写入接口清单；某次接口为何改路径，写入决策或问题记录。
- Redis 当前缓存哪些数据，写入技术选型；缓存污染如何发生和修复，写入专题或问题记录。
- 当前部署命令写入 README；从手动 jar 演进到多阶段构建的过程写入部署专题或复盘。
- 前端当前应实现什么，写入前端规格；某个切片的实际验收证据写入复盘或提交记录。

过程文档中的“当前”只代表记录产生时的状态。文首必须标明历史性质，并链接最新事实入口。

## 3. 记录模板

### 问题

```markdown
## 问题标题

### 现象与复现
### 根因
### 修复
### 验证证据
### 影响范围与后续
```

### 决策

```markdown
## yyyy-MM-dd：决策标题

### 背景与约束
### 候选方案
### 决定及原因
### 适用边界
### 重新评估条件
### 当前代码落点
```

### 实践或专题

```markdown
# 标题

> 文档状态：历史记录 / 持续维护专题
> 当前事实入口：...

## 解决的问题
## 当前代码落点
## 核心机制
## 验证方法
## 风险与边界
## 可复用检查清单
```

### 复盘

```markdown
# 阶段复盘

> 文档状态：历史记录
> 记录阶段：...
> 当前事实入口：...

## 目标与实际结果
## 关键决策
## 验证证据
## 未完成项
## 对下一阶段的约束
```

## 4. 写入前的源码核对

- 接口：Controller、DTO、VO、`Result`、`PageResult`。
- 权限：`WebMvcConfig`、`JwtTokenInterceptor`、登录上下文。
- 状态：枚举、Service 状态校验与条件更新。
- 数据：Entity、Mapper、`assets/schema.sql` 的字段和索引。
- 缓存：`CacheConstants`、`CacheUtil`、各业务 CacheClient、失效调用点。
- 依赖与部署：`pom.xml`、`application*.yaml`、Dockerfile、Compose。
- 完成状态：测试、构建和可复现运行结果。

不要根据类名、TODO、旧计划或单个枚举值推断功能已经完成。

## 5. 一次变更的文档落点

1. 先更新实现和测试。
2. 若外部行为变化，更新当前架构或前端契约。
3. 若形成了值得保留的原因或排障证据，追加一条过程记录。
4. 若改变当前阶段，更新 `documents/CURRENT.md`。
5. 若旧计划失效，将其归档并添加当前入口。

一次变更不要求更新所有文档，只更新受影响的权威来源和必要过程证据。

## 6. 历史记录维护

- 保留当时的错误、假设和阶段结论，不改写成现在时。
- 在文首补充记录阶段、当前入口和“不得作为当前实现依据”的说明。
- 文中出现“后续实现”但功能后来已完成时，可以增加简短编者注或链接；不要删除原始推理。
- 代码示例与当前实现明显不同时，标记为历史示例，并指向当前类；仍宣称“当前代码”的示例必须同步修正。
- 多份记录描述同一问题时，保留证据最完整的一份，其他文档链接过去。
