# 项目文档格式说明

本文档用于统一后续阶段计划、任务清单、过程资产和复盘文档的写法，避免文档越来越多但焦点越来越散。

核心原则：

- 文档服务开发，不为了完整而完整。
- 一个文档只承担一种职责。
- 阶段计划控制方向，任务清单承接待办，过程资产沉淀经验，复盘文档整理阶段成果。
- 后续不要再为每个临时想法新建平级文档，先判断应进入计划、任务清单、过程资产还是专题文档。

## 1. 目录职责

### 1.1 设计文档

路径：

```text
assets/设计文档/
```

用途：

记录项目长期有效的正式设计结论，例如业务流程、领域模型、接口规范、技术选型和包结构。

维护规则：

- 只在设计结论变化时更新。
- 不记录临时想法和开发过程。
- 不替代 Knife4j / OpenAPI 的接口实时说明。

### 1.2 阶段计划

路径：

```text
assets/阶段计划/
```

用途：

记录某个阶段要解决什么问题、按什么顺序推进、做到什么程度算完成。

维护规则：

- 每个阶段保留一份主计划。
- 阶段计划只保留核心任务，不承接全部想法。
- 阶段完成后可以补充收尾行动计划或阶段复盘。

### 1.3 任务清单

路径：

```text
assets/任务清单/
```

用途：

记录候选任务池、优先级、状态和后续迭代方向。

维护规则：

- 适合放 P0 / P1 / P2 待办。
- 适合承接暂缓需求和未来想法。
- 不写成长篇方案，方案细节进入阶段计划或专题文档。

### 1.4 历史归档

路径：

```text
assets/历史归档/
```

用途：

存放已经完成阶段的旧清单、旧规划、阶段性想法文档。

维护规则：

- 原则上只读，不继续作为主要维护入口。
- 如果其中内容仍有价值，应迁移到当前任务清单、设计文档或过程资产。

### 1.5 过程资产

路径：

```text
assets/过程资产/
```

用途：

记录问题、决策、工程实践、技术专题和阶段复盘。

维护规则：

- 具体 Bug 和实现坑进入 `技术实现问题记录.md`。
- 工程边界和方案取舍进入 `工程设计决策记录.md`。
- 可复用工程方法进入 `工程实践记录.md`。
- 系统性技术知识进入 `专题文档/`。
- 阶段结束后新增阶段复盘。

## 2. 阶段计划模板

适用场景：

开始 V3、V4 或某个较大技术增强阶段前使用。

推荐结构：

```md
# Vx 阶段开发计划

## 1. 阶段目标

本阶段主要解决什么问题，控制在 3-5 条。

## 2. 当前基线

项目当前已经完成什么，哪些能力可作为本阶段起点。

## 3. 开发任务拆分

### 3.x 任务名称

#### 背景

为什么要做。

#### 当前问题

现在哪里不够。

#### 目标结果

做到什么算完成。

#### 实现方向

大致怎么做，不写太细代码。

#### 验收标准

如何验证该任务完成。

#### 优先级

P0 / P1 / P2。

## 4. 推荐开发顺序

用列表或流程图说明先做什么、后做什么。

## 5. 阶段验收标准

构建、接口、部署、文档分别如何验收。

## 6. 暂不纳入本阶段的内容

明确不做什么，避免阶段范围失控。
```

停止标准：

- 能指导后续 2-4 周开发。
- 能区分必做、可做、暂缓。
- 不需要把所有实现细节提前写死。

## 3. 任务清单模板

适用场景：

记录候选任务池，或承接某阶段未完成、暂缓、后续增强的内容。

推荐结构：

```md
# Vx 待办任务清单

## P0

### 任务名称

- 背景：
- 当前状态：
- 目标：
- 建议方案：
- 状态：未开始 / 进行中 / 已完成 / 暂缓

## P1

### 任务名称

- 背景：
- 当前状态：
- 目标：
- 建议方案：
- 状态：

## P2

### 任务名称

- 背景：
- 当前状态：
- 目标：
- 建议方案：
- 状态：
```

维护规则：

- 任务清单不追求长篇解释。
- 方案不确定时可以只写“待调研”。
- 已完成任务可以保留状态，也可以在阶段结束后归档。

## 4. 阶段复盘模板

适用场景：

一个阶段基本完成后，用于总结成果、问题、取舍和面试表达。

推荐结构：

```md
# Vx 阶段项目复盘

## 1. 阶段目标与最终结果
## 2. 项目推进过程
## 3. 核心业务或技术闭环复盘
## 4. 关键设计决策复盘
## 5. 典型问题与解决过程
## 6. 当前阶段的边界与不足
## 7. 面试表达整理
## 8. 对后续阶段的启发
## 9. 阶段总结
```

写作要求：

- 不写泛泛总结。
- 每个关键判断要能对应到真实项目经历。
- 面试表达要能直接复述。
- 不堆全部细节，只选最有价值的问题和决策。

## 5. 过程资产记录模板

### 5.1 技术实现问题记录

适用场景：

具体 Bug、报错、实现坑、配置问题。

结构：

```md
## N. 问题标题

### 问题类型
### 现象
### 根因
### 修复方式
### 验证方式
### 经验沉淀
```

### 5.2 工程设计决策记录

适用场景：

职责边界、方案取舍、模块依赖、状态流转原则。

结构：

```md
## N. 决策标题

### 背景
### 冲突点
### 可选方案
### 最终决策
### 适用原则
### 当前项目落点
```

### 5.3 工程实践记录

适用场景：

从具体问题中抽象出的可复用工程方法。

结构：

```md
## N. 实践标题

### 适用问题
### 当前项目问题
### 核心思路
### 落地方案
### 适用原则
### 当前项目后续落点
### 面试表达素材
```

### 5.4 专题文档

适用场景：

某项技术或工具的系统用法，例如 Redis 缓存、Docker 部署、MyBatis-Plus 分页。

结构：

```md
# 专题名称

## 1. 解决什么问题
## 2. 当前项目如何使用
## 3. 核心配置或代码示例
## 4. 常见问题
## 5. 后续项目复用清单
```

## 6. 新文档创建判断规则

新增文档前先判断：

- 如果是长期有效的设计结论，放入 `assets/设计文档/`。
- 如果是某阶段路线图，放入 `assets/阶段计划/`。
- 如果是候选任务池，放入 `assets/任务清单/`。
- 如果是开发经验、问题、决策或专题，放入 `assets/过程资产/`。
- 如果是旧阶段资料且不再主动维护，放入 `assets/历史归档/`。

避免的做法：

- 不要在 `assets/` 根目录继续堆新 Markdown。
- 不要为一个临时想法单独建规划文档。
- 不要把完整对话复制进文档。
- 不要让阶段计划同时承担任务池、技术教程和复盘三种职责。

## 7. 当前项目目录约定

```text
assets/
├── schema.sql
├── 设计文档/
├── 阶段计划/
├── 任务清单/
├── 历史归档/
├── 过程资产/
├── 结果资产(设计)/
└── 草稿资产/
```

说明：

- `schema.sql` 保留在 `assets/` 根目录，因为 Docker Compose 会挂载该路径作为 MySQL 初始化脚本。
- `设计文档/` 承接当前有效设计。
- `阶段计划/` 承接阶段路线图。
- `任务清单/` 承接后续待办池。
- `历史归档/` 保留旧阶段文档。
- `过程资产/` 沉淀经验和复盘。
- `结果资产(设计)/` 存放可复用方法论和模板。
